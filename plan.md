# План виконання завдання `Chat with Node.js`

## Що треба зробити

Зібрати чат-додаток із клієнтом і сервером, де:

- користувач вводить `username`;
- ім'я зберігається в `localStorage`;
- кожне повідомлення має `author`, `time`, `text`;
- є кімнати: `create / rename / join / delete`;
- новий користувач бачить попередні повідомлення в кімнаті.

## Що варто зробити спочатку

Оскільки в репозиторії майже немає готової структури, найпростіше йти так:

1. Підготувати структуру проєкту.
2. Підняти HTTP-сервер на Node.js.
3. Додати realtime-обмін повідомленнями.
4. Реалізувати кімнати.
5. Зберігати історію повідомлень по кімнатах.
6. Зробити клієнтський інтерфейс.
7. Перевірити основні сценарії.

## Покроковий план

### 1. Продумати архітектуру

Перед кодом зафіксуй мінімальну модель даних:

- `users`: тимчасово можна не зберігати окремо, достатньо `username` на клієнті;
- `rooms`: масив або об'єкт кімнат;
- `room`: має `id`, `name`, `messages`;
- `message`: має `author`, `time`, `text`.

Приклад:

```js
{
  rooms: [
    {
      id: 'general',
      name: 'General',
      messages: [
        {
          author: 'Serhii',
          time: '2026-05-13T10:00:00.000Z',
          text: 'Hello',
        },
      ],
    },
  ],
}
```

### 2. Підготувати структуру файлів

Зручно розділити так:

- `src/index.js` - точка входу сервера;
- `src/server/` - логіка сервера;
- `src/public/` - клієнтські файли `html/css/js`;
- `src/data/` або окремий модуль - тимчасове зберігання кімнат і повідомлень.

Мінімум, який реально знадобиться:

- `src/index.js`
- `src/public/index.html`
- `src/public/styles.css`
- `src/public/app.js`

### 3. Підняти базовий HTTP-сервер

На цьому етапі потрібно:

1. Створити Node.js сервер.
2. Налаштувати віддачу `index.html`, `styles.css`, `app.js`.
3. Перевірити, що сторінка відкривається в браузері.

Ціль етапу: браузер уже показує просту сторінку чату.

### 4. Додати realtime для чату

Для чату потрібен обмін даними в реальному часі. Найзручніше:

- або `WebSocket`,
- або `socket.io`, якщо в завданні немає обмеження на бібліотеки.

На цьому етапі реалізуй:

1. Підключення клієнта до сервера.
2. Подію відправки повідомлення.
3. Подію отримання повідомлення всіма користувачами в кімнаті.

### 5. Зробити username і `localStorage`

На клієнті:

1. Покажи форму введення імені.
2. Після введення збережи ім'я в `localStorage`.
3. При наступному відкритті сторінки підтягуй це ім'я автоматично.

Логіка:

- якщо `username` є в `localStorage`, одразу показуй чат;
- якщо немає, спочатку показуй форму входу.

### 6. Реалізувати відправку повідомлень

Коли користувач надсилає повідомлення:

1. Клієнт бере `username`, `text`, активну `roomId`.
2. Відправляє дані на сервер.
3. Сервер створює об'єкт повідомлення:

```js
{
  author: username,
  time: new Date().toISOString(),
  text,
}
```

4. Сервер додає його в історію кімнати.
5. Сервер розсилає повідомлення всім користувачам у цій кімнаті.

На UI виводь:

- автора;
- час;
- текст.

### 7. Реалізувати кімнати

Потрібні 4 дії:

1. `create room`
2. `rename room`
3. `join room`
4. `delete room`

Краще робити саме в такому порядку:

1. Спочатку `create`
2. Потім `join`
3. Потім `rename`
4. Наприкінці `delete`

Для кожної кімнати тримай:

- `id`
- `name`
- `messages`

### 8. Показувати історію повідомлень у кімнаті

Це одна з ключових вимог.

Коли користувач заходить у кімнату:

1. Сервер знаходить кімнату.
2. Віддає всі її попередні повідомлення.
3. Клієнт очищає поточний список повідомлень.
4. Клієнт рендерить повну історію.

Тобто новий користувач має побачити не тільки нові повідомлення, а й старі.

### 9. Оновлення списку кімнат на клієнті

Коли кімнату:

- створили,
- перейменували,
- видалили,

клієнт повинен оновити список кімнат без перезавантаження сторінки.

Зручно зробити окрему серверну подію типу:

- `roomsUpdated`

і на клієнті після неї перемальовувати список.

### 10. Продумати поведінку після видалення кімнати

Тут важливо не залишити користувача в "битому" стані.

Якщо видаляється активна кімната:

1. автоматично перевести користувача в дефолтну кімнату;
2. або вибрати іншу доступну кімнату;
3. або створити `General`, якщо кімнат більше немає.

Найпростіший варіант: завжди мати одну дефолтну кімнату, яку не можна видалити.

### 11. Зробити мінімальний, але зручний UI

Потрібні блоки:

- форма для `username`;
- список кімнат;
- кнопка створення кімнати;
- кнопки перейменування і видалення кімнати;
- зона повідомлень;
- форма надсилання повідомлення.

Мінімальна логіка інтерфейсу:

- активна кімната має бути виділена;
- повідомлення мають прокручуватись вниз;
- порожні повідомлення відправляти не можна.

### 12. Додати базову валідацію

Перевір:

- `username` не порожній;
- `room name` не порожня;
- `message text` не порожній;
- не можна створювати дві кімнати з однаковою назвою, якщо ти так вирішиш у логіці;
- не можна перейменувати кімнату в порожнє значення.

### 13. Протестувати основні сценарії вручну

Перевір мінімум:

1. Ввід `username` і відновлення з `localStorage`.
2. Надсилання повідомлення.
3. Відображення `author / time / text`.
4. Створення кімнати.
5. Перехід у кімнату.
6. Перейменування кімнати.
7. Видалення кімнати.
8. Історія повідомлень після входу в кімнату.
9. Робота в двох вкладках браузера одночасно.

### 14. Перед здачею

1. Прогнати `npm test`.
2. Перевірити форматування.
3. Переконатися, що немає мертвого коду.
4. Перевірити, що застосунок стартує через `npm start`.

## Рекомендований порядок реалізації

Щоб не загрузнути, роби в такому порядку:

1. Статична HTML-сторінка.
2. HTTP-сервер, який її віддає.
3. Ввід `username` + `localStorage`.
4. Одна дефолтна кімната `General`.
5. Надсилання повідомлень у цю кімнату.
6. Історія повідомлень у `General`.
7. Створення нових кімнат.
8. Перемикання між кімнатами.
9. Перейменування кімнат.
10. Видалення кімнат.
11. Полірування UI і перевірки.

## Що краще не ускладнювати

Для цього завдання достатньо:

- зберігати дані в пам'яті сервера;
- не підключати базу даних;
- не робити авторизацію;
- не робити окрему систему користувачів на бекенді.

Якщо вимога про постійне збереження не вказана, in-memory зберігання вистачить.

## Мінімальний результат, який уже можна вважати готовим

Завдання можна вважати виконаним, якщо:

- користувач вводить ім'я;
- ім'я лишається після перезавантаження;
- є хоча б одна кімната;
- можна створювати, перейменовувати, відкривати й видаляти кімнати;
- повідомлення мають `author`, `time`, `text`;
- при вході в кімнату видно старі повідомлення;
- два відкриті клієнти бачать оновлення в реальному часі.
